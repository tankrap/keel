keel vs. git, Entire & Sourcegraph

These are the numbers, measured on real repositories, alongside an honest account of where the incumbents win.

The honest read: as a place to store bytes, git wins — decisively at scale (~4× smaller on the kernel), because delta+pack compression is its years-hardened home turf, and its index makes status a touch faster too. keel ingests ~2× faster (it trades size for speed) but its edge is not storage. It's everything in the next two sections — relevance, the live graph, the fused brief — which git has no equivalent for.
Update — keel repack (delta compression). keel now has a git gc-style pass that re-stores blobs as copy/insert byte-deltas — below the content-address layer, so every read reconstructs and re-verifies BLAKE3 and can never serve wrong bytes. Two passes: same-path (each version vs its predecessor) and cross-path similarity (a MinHash sketch finds a near-duplicate base for copies/generated files). On a real 300-commit history it cut store size −36% (20.7 MB → 13.2 MB), zero corruption (1756 HEAD files exported byte-identical to git's), and reconstruction adds only ~55 µs per delta blob — sub-millisecond for a brief. It narrows the gap but doesn't close it: git's packfile still wins (its full-history objects are smaller than keel's), because git deltas across every object with a name-and-size heuristic keel's two passes only approximate. Storage stays git's turf — this removes most of the overhead without pretending to beat it.

The fused brief — context git and Entire don't compute

Given a task and a symbol, keel returns the target plus the definitions it transitively calls across files (resolved by the language sidecar), budget-bounded. An agent gets the exact neighborhood instead of grepping a 30-million-token repo. Sample: n=100 substantial functions on VS Code /src, each with at least one cross-file callee.

Liveness is the whole game. keel's graph and brief reflect the uncommitted working tree — the callee you just edited but haven't committed. This is measured, not asserted: keel's write-path-live fetch answered a compound "behavior + is-it-safe" question a static index gets nothing on.
Capability matrix

Who has which half

git stores code. Entire (the ex-GitHub-CEO project) layers agent sessions onto git via a shadow branch. Sourcegraph indexes committed code for search. keel is the only one that fuses code + graph + sessions into one live, retrievable substrate — the thesis that storage is commodity and the fusion is the moat.

The compounding advantage · eval-harness results

Flywheel & coordination

These come from keel's evaluation harness (the layer that de-risked the thesis before the system was built), not the live Rust measurements above — labelled honestly as such. They are what a session store (Entire) and a static index (Sourcegraph) each lack.

Flywheel — a relevant prior session lifts a related task
0 → 72%
Graph retrieval (session ↔ symbol/pattern links) recovers a related task to ~72%, against 40% for naive text top-1 and a 75% oracle ceiling. The knowledge lives only in the session — and only the fused graph can retrieve it.
Coordination — parallel-agent conflict cost vs git
1.5–9.7×
Reservations piggybacked on the brief (free when uncontended) cut conflict cost 1.5–4.2× at two agents and up to 9.7× at fleet scale — git has no before-the-fact coordination at all.
Methodology & caveats

What was and wasn't measured

  • Storage & commands are like-for-like: identical working trees, fresh stores, apparent-byte sizing. status is the median of 5 warm runs. git is init/add/commit/gc; keel is init/commit.
  • git wins on store size — delta+pack compression. keel is faster to ingest and competitive on status; its value is the fused context, not the bytes.
  • Relevance is a sample of n=100 functions (each with a cross-file callee); slice size and latency are reported as median / p90, not a best case. Graph edges are the full count over the whole tree.
  • Entire was installed and run (go install …/entire): it hooks git and captures agent sessions to a entire/checkpoints/v1 shadow branch. It is session capture/observability — no relevance graph or brief to benchmark against keel's.
  • Sourcegraph is a hosted static index; its rows reflect its committed-index design (0% on uncommitted state).
  • Flywheel & coordination are eval-harness numbers, labelled separately from the live system measurements.
  • Not yet at scale: C relevance-slicing over the whole kernel (the definition index is bounded); tuning, not a wall.
Reproducibility. Storage/scale: cargo run --release -p keel-store --example scale_bench -- <dir>. Relevance + graph: … --example system_bench, -p keel-graph --example c_scale. git head-to-head: fresh GIT_DIR, one commit, gc.
keel is a research build — local, not yet pushed. Numbers are from a single machine; treat as directional, reproducible via the commands above.
